# dismoji — Emoji Kitchen mashup tab for Discord

**Status:** design approved, not yet implemented
**Date:** 2026-07-25
**Verified against:** Vencord `4b9c27d905d6255141617546227a56073916ebd4` (2026-07-20)

## Summary

A Vencord userplugin adding a tab to Discord's expression picker that lets you
browse Google Emoji Kitchen mashups and insert them into a message. Pick a left
emoji, browse its ~475 real mashup images, click one to send.

Distributed as a shareable userplugin: others can install it, so it needs a
README, settings, and sane defaults.

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Mashup source | Emoji Kitchen pre-rendered pairs only | Hand-designed art; client-side compositing looks like glued stickers |
| Scope | Unicode emoji only, no custom server emoji | Kitchen has no assets for arbitrary uploads |
| Send method | Insert gstatic URL into message box | Zero upload, no permissions needed, works in every channel |
| Picker flow | Pick left → grid of valid partners as real mashup images | Browse outputs not inputs; no dead ends |
| Pair index | Bundled, generated by a repo script | 346 KB gzipped — small enough that runtime hosting isn't worth owning |
| Mount | Picker tab primary, chat-bar button fallback | Tab patch is the fragile part; fallback keeps plugin alive |

- `src/userplugins` is a first-class build path — `scripts/build/common.mjs:148`
- `DataStore` (IndexedDB wrapper) — `src/api/DataStore/index.ts`

- Toolchain: Node >=22, pnpm 11.9.0 — `package.json:83-86`

**CSP.** `www.gstatic.com` is *not* in Vencord's allowlist
(`src/main/csp/index.ts:22-64`), so previews are blocked by default. The
supported remedy is the renderer call

```ts
VencordNative.csp.requestAddOverride("https://www.gstatic.com", ["img-src"], "Emoji Mashup")
```

with in-tree precedent at `src/components/settings/tabs/themes/CspErrorCard.tsx:30`.
It triggers a native "Vencord Host Permissions" dialog requiring the user to tick
a trust checkbox (`src/main/csp/manager.ts:71`). Do **not** use the undocumented
`CspPolicies` mutation hatch — no in-tree plugin uses it.

**Dataset** (measured on the real 94 MB `xsalazar/emoji-kitchen-backend@main:app/metadata.json`):

- 619 supported emoji — *not* the full Discord emoji set
- 147,000 unique latest pairs (293,586 directed records; each pair appears under both emoji)
- 43 distinct release dates, most recent `20260128`
- ~475 partners per emoji on average
- Trimmed index, as actually built: 783 KB packed, **375 KB gzipped**, 500 KB base64.
  (An earlier figure of 346 KB gzipped covered only the pair array and omitted the
  emoji/name/date tables.)

**URL rule** — verified against all 293,586 records (100% match) and live HTTP:

```
https://www.gstatic.com/android/keyboard/emojikitchen/{date}/{L}/{L}_{R}.png
where L = codepoint.split("-").map(c => "u" + c).join("-")
```

Every codepoint *component* takes a `u` prefix. `263a-fe0f` → `u263a-ufe0f`;
`1f62e-200d-1f4a8` → `u1f62e-u200d-u1f4a8`. The naive `u{whole-codepoint}` form
matches only 75.9% of pairs and 404s on the remaining 24.1%. This rule is the
single highest-value unit test in the project.

The pair is symmetric but the **URL is not** — only one of `A_B` / `B_A` exists.
Verified across all 147,000 unordered pairs: exactly one distinct URL each (zero
conflicts), but the URL's left emoji is the lower-indexed one in only 62,501
cases versus the higher-indexed one in 84,499. **Orientation is therefore not
derivable and must be stored** — canonicalising on index order alone would break
57% of lookups. One bit per pair, packed free into the spare bits of the date
byte. `urlFor` owns this so no caller has to know it.

## Architecture

Four units. The view knows nothing about how it is mounted, which is what makes
the fallback cheap.

| Unit | Responsibility | Depends on |
|---|---|---|
| `index.tsx` | Plugin definition, patches, settings, mount selection | Vencord APIs |
| `MashupPicker.tsx` | Two-stage grid UI | props only |
| `kitchen.ts` | Index loading, partner lookup, URL building | bundled index asset |
| `scripts/build-index.mjs` | Regenerate index from upstream | nothing at runtime |

`kitchen.ts` is pure data logic — no React, no Discord imports — and is therefore
the only unit that is straightforwardly testable. Its whole surface:

```ts
partnersOf(codepoint: string): Mashup[]      // ~475 results
urlFor(a: string, b: string): string | null  // null = pair does not exist
```

### Mount strategy

No Vencord API exists for adding picker tabs (`src/api/` has `ChatButtons`,
`MessagePopover`, `ServerList` — nothing for the picker). The tab therefore
requires a raw webpack patch matching Discord's *minified* picker component.

**This match string cannot be derived from source.** It must be found against a
running client, and it is what breaks when Discord reships their bundle. No
upstream plugin adds a picker tab, so there is no in-tree precedent to copy.

Mitigation: the picker view is mount-agnostic, and `index.tsx` mounts it two ways
— the tab patch (primary) and a `ChatButtons` chat-bar button (fallback). Vencord
reports patch-application failures, so the plugin can detect the break and
surface the fallback automatically. A Discord update degrades the plugin to
"works via a button" rather than "broken".

## Data

### Build time — `scripts/build-index.mjs`

Run manually, never at runtime. Downloads upstream `metadata.json`, keeps only
`isLatest` combinations, canonicalises pairs (`left < right`) so each is stored
once, and emits a packed binary:

```
[header]        magic + version
[emoji table]   619 x codepoint string                    ~8 KB
[name table]    619 x alt + keywords (for search)         ~30 KB
[date table]    43 x "YYYYMMDD"                           344 B
[pair records]  147,000 x <u16 lo, u16 hi, u8 flags>      718 KB
                flags = dateIndex (bits 0-6) | orientation (bit 7)
                orientation 0 = URL is lo_hi, 1 = URL is hi_lo
```

Both emoji are stored as **indices into the emoji table**, not codepoints — this
is what makes a record 5 bytes rather than ~40. Everything else in the upstream
record (`gStaticUrl`, `alt`, `leftEmoji`, `rightEmoji`, `gBoardOrder`) is
derivable and is discarded.

The script asserts invariants (619 emoji, ~147k pairs, 43 dates) and HEAD-checks
a random sample of built URLs against live gstatic, so an upstream format change
fails the build loudly instead of shipping broken.

### Embedding

Vencord builds with esbuild into a single bundle, so the index ships as a
gzipped-base64 string constant, decompressed at runtime via
`DecompressionStream("gzip")`. Cost: **500 KB of source text** added to the
Vencord bundle. This is the honest price of the bundling decision.

If that becomes a problem, the known lever is encoding pair existence as an
upper-triangular bitmap (619x619 → 24 KB) with dates in a parallel 6-bit array,
landing near 60 KB gzipped. Deliberately not built up front: real complexity for
a size that is already acceptable, and it is a drop-in swap behind `kitchen.ts`.

### Runtime

Decompression and adjacency-map construction happen on **first tab open**, not at
plugin start — no reason to charge users who never open the tab. ~294k entries, a
few MB, roughly 50-100 ms once. Everything after is a hash lookup.

## UX

### First open — permission gate

Check whether `www.gstatic.com` is allowed for `img-src`. If not, the tab shows a
short explainer with an *Allow previews* button triggering Vencord's consent
dialog.

This is a soft prompt, never a wall. **CSP only affects local previews** — when
you send a mashup, Discord's embed proxy fetches the URL server-side, so
recipients see the image regardless. A user who declines still has a fully
working plugin; they just pick blind.

### Stage 1 — pick the left emoji

Grid of the 619 supported emoji, grouped by the `category`/`subcategory` already
present in the metadata, with a search box over the bundled name/keyword table. A
*Recent* row on top holds the last 24 mashups sent (FIFO eviction), via `DataStore`.

Rendering these is plain Twemoji — already what Discord draws, no network needed.

Because only supported emoji are shown, every emoji in this grid is guaranteed to
have partners. There are no dead ends even before a pick.

### Stage 2 — pick the right emoji

The chosen emoji pins to a header with a back affordance; the grid repopulates
with its ~475 partners, **each cell rendering the actual mashup PNG**. You browse
outputs, not inputs. The same search box now filters partners.

475 images is the perf hazard: cells use native `loading="lazy"` inside a scroll
container, so opening a partner list never fires 475 simultaneous gstatic requests.

### Send

Click a cell → `insertTextIntoChatInputBox(url + " ")` →
`ExpressionPickerStore.closeExpressionPicker()` → record to recents. This is
exactly the GifPaste shape.

### Scope boundaries

Explicitly **not** building: shuffle/random, favourites (recents covers it),
custom-server-emoji mashups (impossible), multi-emoji stacks (Kitchen is strictly
pairs).

**Settings** stay minimal, since every setting is surface that can break:

- `sendMode`: insert URL into message box (default) | copy the URL to clipboard.
  Both modes operate on the URL, never the image bytes — no fetching on send.
- `autoClose`: close picker after sending (default true)

## Failure handling

| Failure | Behaviour |
|---|---|
| Tab patch does not apply | Detect, fall back to chat-bar button, one-time notice |
| User declines CSP consent | Previews blank; sending still works; inline hint |
| Index fails to decompress | Tab shows error state, plugin otherwise inert |
| Individual asset 404s | `onError` hides the cell |

The last row is a confirmed real risk, not hypothetical: two live 404s were hit
during verification of the naive URL rule. A bundled index can also drift from
what gstatic actually serves.

## Testing

- **`kitchen.ts`** — real unit tests. Highest-value case is a table test of the
  `u`-prefix-per-component URL rule, including `-fe0f` and `-200d-` sequences.
  This rule has already produced one bug.
- **`build-index.mjs`** — invariant assertions plus live HEAD sampling.
- **UI and patches** — manual only. No pretence of automation.

## Build sequence

Risk-first. Step 1 exists to invalidate the design cheaply if it is going to be
invalidated at all.

1. **Spike the tab patch.** Renders "hello" in a picker tab, nothing else. If
   this fails, take the chat-bar mount and lose a day, not a week.
2. `build-index.mjs` + `kitchen.ts` + tests — pure, offline, independently verifiable.
3. `MashupPicker.tsx` — the two-stage grid.
4. CSP gate, send path, recents.
5. Fallback mount, settings, README.

## Prerequisite

The stock Vencord installer ships a prebuilt bundle that **cannot load custom
plugins**. Running this requires cloning Vencord, building from source with pnpm,
and injecting that build. One-time setup, but it changes how Vencord updates
thereafter. The README must lead with this.

## Licensing — decided

Neither `xsalazar/emoji-kitchen` nor `xsalazar/emoji-kitchen-backend` has a
licence file (confirmed: no LICENSE tracked in git; GitHub API reports
`spdx_id: NONE` for both). No licence means all rights reserved by default.

What the plugin would redistribute is a table of *facts* — which pairs exist and
on what date. The images are only hot-linked, exactly as the public
emojikitchen.dev does. Assessed risk is low but non-zero.

This is a judgement call, not legal advice.

**Decision: ship with clear attribution.** The README credits
`xsalazar/emoji-kitchen` as the metadata source and Google as the artwork author,
and `build-index.mjs` records provenance in the generated file's header. If
xsalazar later adds a licence, honour it.

Rejected: generating the index at install time (reintroduces the network
dependency the bundling decision exists to remove, for no legal gain — the
derived facts are the same either way).

Worth doing separately, not a blocker: open an issue asking xsalazar to add a
licence.
